Server (server/src)

The entry point is main.ts. A global ValidationPipe strips unknown request fields. app.module.ts wires the modules together.

Core

tracks/

  • List, detail, create, update, delete routes
  • Favorites and archive (PATCH :id/archive)
  • Audio and artwork streaming
  • track.service.ts: queries and sort order
  • track.view.ts: response shaping

albums/, people/

  • Albums with their tracks; album cover replacement
  • People grouped by role: composer, artist, lyricist, actor
  • Rename and delete a person (delete blocked with 409 while tracks are linked)

playlists/

  • Add, remove, reorder tracks
  • Rejects archived tracks with 409

Data flow

  1. A page calls a hook in lib/queries.ts.
  2. The hook calls api.ts, which requests /api/.... Vite proxies that to the server in dev.
  3. The controller validates input with a DTO. The service runs Prisma queries.
  4. A *.view.ts file shapes the response. TanStack Query caches it.
  5. Writes call a mutation hook, which invalidates the affected queries.

Admin gating

Admin-only features are gated in two places:

  • Web: hides or disables edit, delete, archive, and the archived-track filter.
  • Server: AdminGuard protects the write routes.
The read-side filter for archived tracks is a display filter, not a security boundary. The GET endpoints are not guarded, so the server still returns archived tracks to anyone who calls them directly.

Tests

The server has Vitest specs next to the code, such as normalize.spec.ts, audio-path.spec.ts, and auth.service.spec.ts. The web app has no test suite. It relies on typechecking and lint.
